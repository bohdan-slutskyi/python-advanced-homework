# Архитектурные решения — LMS №271

**Состояние на 17.11.2026:** решения D01–D14 зафиксированы; начальная ER-схема реализована в Django-моделях и MySQL-миграциях, API регистрации и объявлений проверен. Сервисы жизненного цикла бронирований, конкурентного подтверждения, отзывов и аналитики пока не реализованы; соответствующие разделы описывают запланированное поведение. Требования LMS и дополнительные проектные решения выделены отдельно.

## Основания проектирования

- **LMS:** Django_LfS_Project (1).pdf, с. 4–7 — обязательное ядро, с. 5 и 8 — дополнительные функции, с. 9–11 — рубрика. История поиска/просмотров дополнительна по постановке, но присутствует в колонке оценки 1 (с. 10). Docker/AWS — дополнительные технологии и критерий оценки.
- **Примеры:** Project_ описание ожидаемого результата с примерами.pdf, с. 1–12 — архитектурные иллюстрации, а не дополнительные самостоятельные требования; схемы на с. 9–12 иллюстративны.
- **Дополнительные рекомендации по архитектуре:** материалы Python Advanced 39: 3NF, пять приложений, Custom User + штатные Django Groups, soft delete, ограничения, индексы, сроки и отзывы. Обязательный объём определяется спецификацией LMS.
- **Официальная совместимость:** https://docs.djangoproject.com/en/5.2/topics/auth/customizing/ ; https://docs.djangoproject.com/en/5.2/ref/databases/ ; https://docs.djangoproject.com/en/5.2/ref/models/constraints/ ; https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html . Документация для сверки семантики; версии зависимостей зафиксированы в `pyproject.toml` и `uv.lock`.

## Реестр решений и последствий

| ID | Проблема / решение | Основание и уровень | Модель / API / тест |
|---|---|---|---|
| D01 | **Одна сущность Listing без отдельной Property.** Один долговечный Listing представляет сдаваемую единицу и объявление; адрес, вид жилья и комнаты хранятся только там. Повторная публикация — изменение is_active, а не пересоздание. | В LMS задано объявление, отдельная Property не требуется. Без верификации объекта дополнительная сущность Property не предотвращает создание дубликатов. | Связь с Property отсутствует; проверены сохранение истории, soft delete и права владельца. Отдельная Property нужна только при введении проверенной идентичности/смены собственника. |
| D02 | **Custom User до первых миграций**, уникальный нормализованный email как логин, обязательное display_name; без User.role. **Стандартные auth.Group Tenant и Landlord** через штатную M2M; обе группы у одного пользователя допустимы. | Регистрация и права: LMS с. 4; для групп применена стандартная Django auth.Group (материалы Python Advanced 39). Django AUTH_USER_MODEL должен появиться в 0001_initial приложения accounts. | Регистрация автоматически назначает Tenant; Landlord присваивает только staff/admin/защищённый seed, не публичная смена группы. Объектные права проверяются отдельно; тест оба membership. |
| D03 | **Аутентификация JWT** для API/Postman с refresh-blacklist logout, коротким access token. | LMS разрешает JWT или сессии (рубрика с. 9–10); способ — технический выбор. | login выдаёт токены, logout отзывает переданный refresh token; уже выданный access token остаётся действующим до истечения срока, это тестируется и честно документируется. |
| D04 | **Listing сохраняет идентичность и историю:** deleted_at nullable, is_active независим. DELETE — бизнес-soft-delete, не физическое удаление; из публичных выборок исключать удалённые/неактивные. При удалении не стирать брони/отзывы. | LMS: CRUD и активность объявления, с. 4; сохранение истории бронирований и отзывов. | PATCH/DELETE доступны владельцу; восстановление удалённого объекта через публичный API **не поддерживается**; временная публикация управляется is_active. Доступ участников к историческим бронированиям и отзывам планируется через отдельные endpoints. |
| D05 | **Заезд/выезд — даты [check_in, check_out)**; check_out не входит в проживание, соседние интервалы не конфликтуют. check_in не раньше текущей даты в Europe/Berlin, check_out > check_in; максимальная длительность 365 ночей и горизонт старта 365 дней — дополнительные ограничения приложения, не заданные LMS. | LMS задаёт работу с датами, но не конкретные ограничения по длительности и горизонту бронирования. | Booking Dates; API 400 при неверной дате/диапазоне, граничные тесты и DST/localdate. |
| D06 | **Статусы:** PENDING → CONFIRMED или REJECTED или CANCELLED; CONFIRMED → CANCELLED (только до check_in). Термин «завершённое проживание» — вычисляемый CONFIRMED с check_out <= localdate; отдельный COMPLETED status не нужен. CANCELLED/REJECTED терминальны. | LMS создание, подтверждение, отказ, отмена с. 4,7; точные переходы — инженерный выбор. | Transition service и POST confirm/reject/cancel, 409 для недопустимого перехода. «Активные» = будущие PENDING + ещё не завершённые CONFIRMED; «завершённые» = прожитые CONFIRMED; отклонённые/отменённые/просроченные PENDING доступны в истории/по status. |
| D07 | **Отмена Tenant** для PENDING и CONFIRMED только когда Europe/Berlin localdate < check_in, то есть до начала календарного дня заезда. Нет штрафов/платежей. Landlord может отклонить только PENDING; отменять CONFIRMED за жильца нельзя в MVP. | LMS требует «до определённой даты», но срок не задаёт; это установленная политика приложения. | POST cancel, тест до полуночи/в день заезда, запрет чужой отмены, повторный вызов 409. |
| D08 | **PENDING не резервирует даты.** Несколько заявок на пересекающийся период допустимы; только CONFIRMED блокирует даты. Confirm возможен только для активного/неудалённого Listing и будущего заезда. | LMS не задаёт модель hold, выбран простейший проверяемый жизненный цикл. | Поиск конфликтов только среди CONFIRMED; тест двух PENDING и одного успешного confirm. |
| D09 | **Конкурентность MySQL:** все create/confirm/cancel и изменения доступности Listing используют общий порядок блокировки: transaction.atomic → SELECT ... FOR UPDATE строки Listing по PK → повторная проверка Booking и пересечений при confirm → изменение Booking → commit. При двух confirm сериализует Listing; READ COMMITTED и InnoDB. | MySQL не умеет CHECK пересечения разных строк; Django рекомендует READ COMMITTED. Использование транзакционной блокировки — проектное техническое решение, не отдельное требование LMS. | SELECT FOR UPDATE выполняется внутри atomic; после блокировки повторно читаются актуальные данные. Индекс для конфликта по listing_id/status/dates, параллельные TransactionTestCase на реальном MySQL и отдельных соединениях; обработка deadlock/timeout и rollback предусмотрена сервисом. |
| D10 | **Отзыв строго по одной Booking**, OneToOne; только tenant этой подтверждённой брони и после check_out <= localdate. Рейтинг 1–5 + comment; владелец Listing не может удалять/редактировать чужой отзыв. | LMS: отзывы после проживания, с. 5, 7. Подтверждённая завершённая бронь служит техническим условием допуска к отзыву, но не доказывает физического присутствия гостя. | UNIQUE review.booking_id и CHECK 1..5; получение отзывов и среднего через Booking → Listing. В проектном API допускается редактирование собственного отзыва; удаление пользователем или владельцем объявления не предусматривается. |
| D11 | **Персональные данные и статистика:** SearchEvent только непустой нормализованный текст запроса (без IP, cookies, user agent) и необязательный user; ViewEvent — Listing, необязательный viewer и timestamp. Анонимные события без идентификации. | Дополнительные функции LMS с. 5,8; статистика вынесена в самостоятельное приложение для разделения ответственности. | События планируются при поиске и открытии карточки; бизнес-состояние Listing/Booking при GET не изменяется. Топы вычисляются агрегированием без полей total_views/avg_rating; доступ к личной истории — только владельцу, к общим топам — агрегировано. Политика хранения и удаления событий определяется перед развёртыванием. |
| D12 | **Мелкие, проверяемые ограничения** в MySQL плюс валидаторы в Django/DRF. PK BigAutoField, FK PROTECT для исторических связей, низкокардинальные boolean/status без отдельного одиночного индекса, Choices для статусов и типов. | 3NF, целостность PK/FK, ограничения MySQL и совместимость Django. | DB CHECK: price > 0, rooms > 0, check_in < check_out, rating 1..5; UNIQUE email, Review.booking_id, стандартной пары User-Group. Диапазоны относительно сегодняшнего дня, право доступа и пересечение — в сервисе, не в CHECK. |
| D13 | **Один владелец Listing не меняется через PATCH.** Tenant не может бронировать собственный Listing даже при наличии обеих групп. Удаление/деактивация Listing не аннулирует уже подтверждённые брони; новые и неподтверждённые нельзя подтверждать. | Не прямой текст LMS; дополнительная политика прав доступа и сохранения истории. | Object permissions и сериализатор read-only landlord_id; тест двойной роли, истории, попытки self-booking и DELETE при существующей броне. |
| D14 | **Дубли адресов не определяют физическую идентичность.** UNIQUE по адресу не используется из-за возможных комнат и смены владельца; защита от ложного повторного создания с целью сброса рейтинга невозможна без верификации объектов, вне текущего объёма проекта. | Ограничение модели без верификации физической идентичности объекта. | Созданная Listing имеет неизменяемый id и историю, soft delete не стирает отзывы; риск злоупотребления дубликатами остаётся ограничением выбранной схемы. |

## Нормализация и ограничения гарантии

- В каждой пользовательской таблице атомарные поля зависят от собственного PK; данные арендатора не повторяются в Booking, оценка и автор не дублируются в Listing, агрегаты вычисляются. Review получает владельца от Booking. Соответствие 3NF проверено по Django-моделям и миграциям.
- Django auth.Group и таблица CustomUser.groups являются **штатными таблицами Django**, а не самописной роле-моделью.
- MySQL не реализует полноценный exclusion constraint по интервалам; запись напрямую в БД в обход сервиса может обойти правило непресечения. Дополнительные таблицы дат и SQL-триггеры не используются.
- MySQL не поддерживает частичные уникальные индексы Django; условная уникальность «только для is_active=true» не гарантируется.
- Получение GET может создавать побочные аналитические события, но не менять сами Listing/Booking; подсчёт просмотров не является условием успешного чтения.
- Физическое присутствие гостя, юридическое право собственности, реальная смена владельца и проверка адреса не подтверждаются в учебном проекте.

## Ограничения и дальнейшее развитие

1. **Получение статуса Landlord:** самостоятельное публичное назначение группы не предусмотрено. В текущей реализации группа назначается через доверенное администрирование.
2. **Срок отмены:** установлено правило отмены до календарного дня заезда в часовом поясе Europe/Berlin. Переходы состояний и проверки этого ограничения запланированы для API бронирований.
3. **Политика аналитики:** сроки хранения событий, доступность агрегатов и информирование о сборе данных определяются перед развёртыванием.
4. **Развёртывание:** Docker и инфраструктура AWS относятся к следующему этапу; развёртывание и оценка затрат пока не выполнены.

**Проверка моделей 17.11.2026:** проверены модельные валидаторы, MySQL CHECK/UNIQUE/FK, индексные поля и case-sensitive Choices; отчёт — [model-review.md](model-review.md). Проверки на MySQL успешны; бизнес-сервисы и конкурентные тесты ещё впереди.

**Следующий этап разработки:** сервисы бронирований и переходов статусов по D05–D09, затем Review по D10 и поиск/фильтры. Для подтверждения корректности конкурентной защиты запланирован тест двух параллельных MySQL-транзакций на одном Listing.
