# Проверка моделей и ограничений — 17.11.2026

**Область проверки:** структура Django/DRF/MySQL проекта LMS №271, модели, миграции, валидаторы, индексы, связи и реализованный API регистрации и объявлений. Сервисы бронирований, отзывов и аналитики в проверенный объём не входят.

## Проверенная структура

| Пункт | Реализация и проверка |
|---|---|
| Модель пользователя и группы | `accounts.User` в `0001_initial`, email UNIQUE, стандартные `auth.Group` Tenant/Landlord, оба membership допустимы |
| ER/3NF | Listing без Property, Booking связан с tenant и Listing, Review OneToOne с Booking (автор и объявление не дублируются), SearchEvent/ViewEvent отдельно |
| Сохранение истории | `Listing.deleted_at` + `is_active`, FK с `on_delete=PROTECT` для Booking/Review; на MySQL фактический DELETE_RULE — NO ACTION |
| Модельные проверки | `Booking.clean()`: даты, 365 ночей/365 дней, Berlin localdate, self-booking и доступность новой заявки; `Review.clean()`: CONFIRMED и завершённое проживание; `SearchEvent.clean()`: нормализация и непустая строка |
| Полевые валидаторы | Цена Decimal > 0; комнаты > 0; рейтинг 1–5; немецкий почтовый индекс ровно 5 цифр; Choices для страны, типа жилья и статусов |
| SQL-ограничения | CHECK для цены, комнат, диапазона дат, рейтинга, страны, типа жилья, статуса, согласованности soft delete, непустого поискового запроса; UNIQUE для email, Review.booking и штатной пары User.groups |
| Строгость Choices | `utf8mb4_0900_bin` на country_code/housing_type/status: SQL отвергает неправильный регистр и лишний пробел. Для email сохранена `utf8mb4_0900_ai_ci` и регистронезависимая уникальность |
| Индексы | `Listing(landlord,deleted_at)`, `Listing(city,district)`, `Booking(listing,status,check_in,check_out)`, `Booking(tenant,status)`, PK/UNIQUE; без отдельного индекса только на boolean/status |
| API-границы | Регистрация назначает Tenant; доступ Landlord и проверка владельца, JWT blacklist, скрытие и soft delete проверены HTTP/API-тестами |

## Как проверено

- Локальная MySQL **26.10.0**, InnoDB: новые миграции `listings.0002/0003`, `bookings.0002/0003` и `statistics.0002` применены к уже существующей тестовой схеме без обнуления данных.
- **21 автоматический тест, 15 параметризованных проверок на MySQL**, включая негативные случаи SQL CHECK/UNIQUE, границы дат, переход календарного дня Berlin, регистрацию, права и soft delete. SQLite применяется для вспомогательных логических тестов с адаптером MySQL-колляции; основная проверка выполняется на MySQL.
- Инспектированы `information_schema.CHECK_CONSTRAINTS`, `STATISTICS`, `COLUMNS`; проверено различие `utf8mb4_0900_ai_ci` и `utf8mb4_0900_bin`.
- Дополнительно успешно выполнены Django system check, проверка отсутствия новых миграций, Ruff check/format и генерация OpenAPI с валидацией.

## Что ещё не реализовано

1. **`Model.clean()` не запускается автоматически при `save()`.** Будущие сервисы создания Booking/Review и событий обязаны явно вызывать `full_clean()` или эквивалентные проверки на уровне сериализатора. Сейчас Booking/Review API отсутствует, поэтому соответствующая бизнес-логика не заявляется как готовая.
2. **Непересечение CONFIRMED и переходы состояний** требуют MySQL-транзакции `atomic → select_for_update(Listing) → свежая проверка бронирований`; нужен параллельный `TransactionTestCase`. SQL CHECK не выражает проверки между несколькими строками.
3. **Оптимизация индексов** требует `EXPLAIN` после наполнения репрезентативными Faker-данными; факт создания индекса не доказывает его эффективность.
4. Поиск, фильтры, API отзывов, дополнительная аналитика, Postman/Faker, Docker и развёртывание запланированы после основного ядра.
5. Локальная конфигурация с отдельным MySQL-пользователем минимальных привилегий не выполнена; в Git секреты отсутствуют.

**Результат:** начальная схема данных, миграции и модельные проверки реализованы и проверены на MySQL. Ограничения ещё не реализованных API и транзакционных сервисов перечислены выше.
