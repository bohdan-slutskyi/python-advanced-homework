# Соответствие требованиям — финальный проект Python Developer (LMS №271)

**Состояние на 17.11.2026.** Реализованы модели и миграции пяти Django-приложений, API регистрации и аутентификации, а также базовый API объявлений. Проверки выполнены на MySQL. Остальные функции в таблице обозначены как частично реализованные или запланированные. Наличие модели не означает наличие работающего API.

## Источники и обозначения

- **LfS** — постановка проекта `Django_LfS_Project (1).pdf`: основной функционал на с. 4–7, дополнительные функции на с. 5 и 8, технические критерии на с. 9–11.
- **Примеры** — `Project_ описание ожидаемого результата с примерами.pdf`. Примеры иллюстрируют возможную реализацию и не добавляют самостоятельных обязательных функций.
- **Python Advanced 39** — материалы занятия, использованные при выборе структуры приложений, связей и проверок.

Статусы: **Реализовано** — функция доступна и проверена; **Модель** — создана и проверена модель, но соответствующий API отсутствует; **Частично** — реализована только часть указанного поведения; **Не реализовано** — запланировано, но ещё не доступно. Для запланированных функций проверки описывают ожидаемые тестовые сценарии, а не результаты уже проведённых тестов.

## Принятые правила предметной области

Следующие решения определяют поведение приложения. Правила, относящиеся к отсутствующим API, пока реализованы только на уровне моделей либо описаны для следующего этапа.

- **Период проживания:** даты `[check_in, check_out)`; день выезда не включается в занятый интервал. Модель ограничивает продолжительность 365 ночами и начало проживания горизонтом 365 дней.
- **Отмена бронирования:** предусмотрена до календарного дня заезда по часовому поясу Europe/Berlin; сервис переходов состояний ещё не реализован.
- **Пересечения бронирований:** заявки `PENDING` не блокируют период, а подтверждённые `CONFIRMED` должны исключать пересечения. Транзакционная проверка при подтверждении ещё не реализована.
- **Права пользователей:** при регистрации назначается Tenant. Группа Landlord предоставляется только доверенным администрированием. Одна учётная запись может состоять в обеих группах.
- **История объявлений:** используется soft delete; исторические связи Booking/Review сохраняются. Уникальность физического объекта по адресу не гарантируется.
- **Отзывы:** предусмотрен один отзыв на подтверждённую и завершённую бронь, оценка от 1 до 5. Модельные проверки есть; публичного API отзывов пока нет.
- **Аутентификация:** JWT с отзывом refresh-токена при выходе; выданный access-токен остаётся действительным до истечения срока.
- **Аналитика:** модели событий допускают анонимные записи и не содержат IP-адресов, cookies или user agent; автоматическая запись событий и агрегаты ещё не реализованы.

## Подтверждённые проверки и ограничения

На 17.11.2026 проверены Django system check, отсутствие изменений схемы после миграций, Ruff check/format и генерация OpenAPI. На MySQL пройдены **21 автоматический тест и 15 параметризованных проверок**. Проверены создание и доступ к объявлениям, регистрация и аутентификация, ограничения базы данных, модельные валидаторы и soft delete.

Поиск и фильтрация, API бронирований и отзывов, конкурентное подтверждение бронирований, запись аналитических событий, генерация Faker-данных, Postman Collection, Docker и облачное развёртывание в эту контрольную точку не входят. Подробности архитектуры и выполненных проверок представлены в [описании модели](architecture/er-model.md), [решениях](architecture/decisions.md) и [отчёте о проверке моделей](architecture/model-review.md).
