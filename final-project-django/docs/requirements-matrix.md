## Принятые бизнес-правила (технический выбор, не цитаты LMS)

1. **Отмена до определённой даты:** LMS не называет длительность окна отмены. Принято: Tenant отменяет PENDING/CONFIRMED до календарного дня check_in по Europe/Berlin; позднее не может. Это проектный выбор, не срок из LMS.
2. **Границы проживания:** принято: даты [check_in, check_out), смежные брони совместимы; политика не является дословным требованием LMS.
3. **Конфликт заявок:** принято: параллельные PENDING допустимы; календарь блокирует CONFIRMED; подтверждение сериализуется блокировкой Listing в transaction.atomic на MySQL READ COMMITTED; проверить реальной гонкой.
4. **Роли при регистрации:** принято: Tenant назначается при регистрации; Landlord — только доверенным staff/seed; публичное повышение роли не предусмотрено. Один User может состоять в обеих группах.
5. **История недвижимости и повторное размещение:** один долговечный Listing с soft delete, без Property; не вводить уникальность по адресу, сохранять Booking/Review; создание дубликата с новым id остаётся риском.
6. **Рейтинг:** принято: один Review на одну завершённую CONFIRMED бронь; создание в день выезда и следующие 30 календарных дней включительно (Europe/Berlin); один пользователь может написать ещё один отзыв после другого проживания; свой отзыв можно редактировать и после срока, удалять через публичный API нельзя.
7. **Аутентификация:** рубрика допускает JWT или сессии; выбран JWT + blacklist refresh при logout; access token действителен до своего expiry.
8. **Счётчики просмотров и история поиска:** реализованы nullable user/viewer, query/просмотр/время; без IP/cookies/UA. Личная история доступна только после JWT. Публичные рейтинги объявлений не содержат viewer, опубликованные поисковые запросы требуют >=3 различных авторизованных пользователей; анонимные события сами порог не удовлетворяют. Срок хранения и уведомление о сборе данных уточнить перед деплоем.
