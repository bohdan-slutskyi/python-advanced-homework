# Целостность моделей и нормализация данных Django (21.11.2026)

**Область:** Django/DRF/MySQL REST backend аренды жилья, LMS №271.
Раздел описывает улучшения модели данных, обратную совместимость API,
миграции и автоматическую проверку.

## Архитектурные решения

**География.** Созданы нормализованные справочники City и District с
уникальностью имён города и пары (город, район). Миграция содержит шесть
проверенных городов: Berlin, Hamburg, Hannover, Köln, Hildesheim, Bonn;
четыре района: Berlin/Mitte, Berlin/Kreuzberg, Hannover/Mitte, Hannover/List.
Добавление других географических единиц — через Django admin,
не автоматически через POST объявлений.

`Listing.city` обязателен, `Listing.district` необязателен. API сохранил
строковые `city`/`district` и нечувствительные к регистру фильтры.
Неизвестный город/район или чужой району город возвращает HTTP 400.
`Listing.clean` и DRF serializer проверяют принадлежность района городу;
MySQL обеспечивает оба FK отдельно, **но прямой SQL способен связать
район с чужим городом** — это известная граница DB-инварианта.

**Старые данные.** До миграции в Homebrew MySQL было 130 Listing и
257 Booking. Значения `district` у многих демонстрационных записей
создавались через `fake.city()` и не проверялись как районы. Исходный
текст сохранён в `legacy_city`/`legacy_district` для аудита/отката;
неподтверждённые пары не включены в справочник. В результате 128
исторических объявлений имеют `district_id=NULL`, но старый ввод
сохранён. Для них поле `district` API теперь выдаёт пустую строку,
а не потенциально неверный район; фильтр по такому старому названию
не сработает. Это документированное изменение **содержимого** API
для неподтверждённых legacy-строк.

**Стоимость.** При создании заявки `create_booking` внутри
`transaction.atomic` и `select_for_update(Listing)` вычисляет
`total_price=Decimal(price_per_night) × nights` для полуоткрытого
интервала `[check_in, check_out)`. Значение сохраняется в Booking
одновременно с PENDING; подтверждение/отмена и изменение цены
объявления его не меняют. Клиент не может задавать `total_price`
через API. Историческая цена неизвестна: **у всех 257 старых бронирований
`total_price=NULL`**, никакого задним числом расчёта не выполнялось.
DB CHECK запрещает ноль и отрицательную сумму; NULL оставлен для
импорта старой истории, поэтому прямой SQL может создать такую запись,
но API-сервис для новых бронирований всегда вычисляет цену.

**Отмена и даты.** MySQL CHECK запрещает `status='CANCELLED'` при
`cancelled_at IS NULL`. Предварительная проверка старых данных выявила
0 таких записей; если они появятся в другой базе, migration preflight
остановит обновление для ручного восстановления проверенной даты.
Лимиты 365 ночей и 365 дней горизонта имеют именованные константы;
бизнес-правило не изменено.

## Доказательства и ограничения

- Перед изменениями создан локальный SQL backup вне Git с mode `0600`.
- Миграции проверены на полном клоне MySQL: 130 Listing, 257 Booking
  сохранились. Затем применены на основной Homebrew MySQL с тем же итогом.
- Справочники после миграции: 6 City, 4 District; 128 legacy районов
  не сопоставлены, 130 исходных городов сохранены в архивных полях.
- На локальной MySQL: `migrate --check`,
  `makemigrations --check --dry-run`, `manage.py check` — PASS.
- Полный автоматический набор **91/91 тестов PASS на временной MySQL**,
  включая 6 новых тестовых методов и исходные конкурентные сценарии.
- Генератор `seed_demo` больше не создаёт районы случайными названиями
  других городов и сохраняет стоимость новых синтетических броней.

- После сквозной сверки обновлён исходный `postman/build_collection.py` и
  шаблоны обоих окружений; дополнительный
  `tests/test_postman_generation.py` проверяет идентичность 41-запросного
  экспорта исходному генератору и наличие пустой переменной
  `booking_total_price`. **Итоговый повторный прогон 91/91 PASS**.
  Импорт в приватный Postman workspace и его полный Runner пока не
  выполнялись.
- На этапе миграции сохраняются для аудита 128 старых названий районов,
  257 старых броней с неизвестной стоимостью, ограниченная начальная
  база городов и прямые SQL-операции в обход сервисов.

## Перенос миграций в существующую облачную среду

1. Проверить статус существующего EC2, применённые миграции, место на EBS,
   а также доступность базы данных и окна обслуживания.
   SSH-доступ; сделать и проверить backup/snapshot **серверной** БД.
   Не заменять серверный MySQL локальным дампом.
2. Проверить `migrate --plan`, наличие неподтверждённых городов,
   CHECK существующих броней и перенести копию серверной базы на
   временный стенд для безопасной репетиции миграций.
3. Остановить запись новых данных, развернуть проверенный commit,
   выполнить миграции ровно один раз. Сопоставить counts, FK,
   CHECK, суммы старых/новых броней, OpenAPI и Postman smoke.
4. При проблеме не применять слепой reset/rollback — сохранить
   диагностику, выбрать согласованное восстановление из backup либо
   отдельную корректирующую миграцию. После проверки остановить EC2.
   До обновления EC2 содержит **предыдущую версию схемы и кода**.

**Граница результатов 21.11:** локальная MySQL подтверждает миграции
и тесты; перенос новых миграций на AWS проверяется отдельно.
Полный Postman Collection Runner на новой схеме не проводился.
